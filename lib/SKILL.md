# 项目罗盘 · 接手一个陌生项目的标准动作

本项目罗盘（Project Compass）要回答的是**接手项目时最费时间的那些问题**，而且每个答案都必须能指回代码里的具体位置。

## 什么时候用它

- 刚加入一个项目，需要快速建立全局认知；
- 接手遗留项目，想知道"哪些地方最危险、先改哪里"；
- 作为技术负责人，需要一份能发给新人的上手指南；
- 作为 AI Agent，在动手改代码前需要项目的结构与约定作为上下文。

## 四步走（每一步都有明确产物）

| 步骤 | 工具 | 产物 | 你得到什么 |
|---|---|---|---|
| 1. 侦察 | `project_compass_scan` | `.project-compass/scan.json` | 技术栈、可执行命令、入口点、测试框架、工程缺口、敏感文件 |
| 2. 解析 | `project_compass_analyze` | `.project-compass/ir.json` | 统一 IR：模块/文件/符号/导入/调用/路由 + 三级依赖图 + 关键流程 |
| 3. 成文 | `project_compass_report` | `docs/project-compass/*.md` + `project-compass.json` | 5 份人读文档 + 1 份机器可读视图 + 检索索引 |
| 4. 追问 | `project_compass_ask` | 带引用的答案 | 任意具体问题的证据链回答 |

项目更新后用 `project_compass_update` 增量刷新；不确定状态时用 `project_compass_status`。

## 阅读顺序建议

1. **先读 `ONBOARDING.md`**：定位、技术栈、10 分钟上手路径、按角色阅读路线。
2. **再读 `ARCHITECTURE.md`**：分层结构、模块依赖表、循环依赖与高风险模块。
3. **需要改某块代码时读 `MODULE_MAP.md`**：该模块的职责、关键符号与对外接口。
4. **要理解某条业务流程时读 `KEY_FLOWS.md`**：入口 → 调用链的时序图与步骤表。
5. **要动手跑起来时读 `GETTING_STARTED.md`**：真实命令、环境变量、排障清单。
6. **要接进 CI 或别的工具时用 `project-compass.json`**。

## 提问的正确姿势

`project_compass_ask` 是**本地混合检索**（BM25 + 向量 + 重排），对关键词敏感。问得好，答得准：

| 不推荐 | 推荐 |
|---|---|
| 这个项目怎么样？ | 用户登录流程经过哪些模块？ |
| 讲讲架构 | `src/api/client.ts` 的 `request` 被哪些模块调用？ |
| 有 bug 吗 | 订单创建的入口路由在哪个文件第几行？ |

答案里的 `citations` 就是证据。**先看证据，再看结论**：如果 `confidence` 是 `low`，说明检索命中不足，应换更具体的符号名/文件名重问，或直接去 `MODULE_MAP.md` 里找。

## 证据纪律（这份报告凭什么可信）

- 跨文件依赖**只认显式 import**；无法静态确定的调用标记为 `unresolved`，不会猜出一条假依赖。
- 每条结论后附 `path:line` 或 `path#symbol`；无证据的推断显式标注"未验证"。
- 报告顶部记录了 LLM 是否参与、验证器丢弃了多少条无据断言。
- 敏感文件（`.env`、`.pem`、`credentials*` 等）**只登记路径，不读取内容**。

## LLM 的使用边界

默认**不调用任何 LLM**，全部结论来自静态证据。只有显式 `withLlm: true` 时，模型才介入写措辞，且：

1. 模型只能使用工具给的"项目事实简报"，不允许补充简报之外的信息；
2. 每条断言必须带 `path:line` 引用；
3. 逐条过验证器，路径/行号/符号对不上的断言**直接丢弃**并计数。

因此：**LLM 关掉时报告依然完整**，只是措辞朴素一些。

## 常见误区

- **不要**把 `unresolved` 当成"没有依赖"：它只表示静态分析无法确定，动态调用、反射、依赖注入都会落到这里。
- **不要**只看模块数量判断复杂度：`ARCHITECTURE.md` 的扇入/扇出与风险分比行数更能说明问题。
- **不要**在代码大改后直接信任旧报告：跑一次 `project_compass_update`，它会告诉你新增/变更/删除了哪些文件。
- **不要**期望它替代人工评审：它给的是地图，不是判决书。

## 与其它工具配合

- 想验证"能不能跑起来、质量够不够上线"：配合质量审计类插件（如 `dsh-qualityforge`）对同一项目做全面测试编排。
- 想让别的 Agent 用上项目上下文：让它先调 `project_compass_ask` 拿带引用的答案，而不是让它通读整个仓库。
